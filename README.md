# doc-agent

AI-агент: преобразует задачу разработки, выгруженную из **Yandex Tracker**
(.doc, реально HTML), в аккуратный .docx-документ для заказчика. Заодно
проверяет, что в задаче есть все обязательные для клиента разделы
(«Потребность клиента», «Детали реализации», «Критерии приёмки»), и
сообщает, чего не хватает.

## Как это устроено

Экспорт «в Word» из Yandex Tracker на самом деле HTML с очень регулярной
разметкой: метаданные (Статус/Тип/Автор/Исполнитель/Проект/...) в таблицах,
а тело задачи — в `<td id="descriptionArea">` с h2-заголовками разделов
(«Потребность клиента», «Детали реализации», «Критерии приёмки» в формате
Given/When/Then-таблицы, «Техническая реализация»). Раз разметка стабильна —
эта структура разбирается **детерминированно**, без ИИ, что надёжнее, чем
просить LLM угадывать структуру по plain-тексту:

```
DEV-XXXXX.doc (HTML-экспорт Yandex Tracker)
   │
   ▼
tracker_parser.py  — детерминированный HTML-парсер: ключ/заголовок задачи,
   │                  метаданные, разделы в порядке документа, включая
   │                  вложенные списки и сворачиваемые блоки (YFM cut/note),
   │                  Given/When/Then-таблицу критериев приёмки -> читаемые
   │                  сценарии
   ▼
[есть --rewrite?] ──нет──▶ builder.py — оформление как есть
   │
   да
   ▼
rewriter.py   — Claude API: переписывает содержимое каждого раздела деловым
   │             языком для заказчика, убирает техжаргон/внутренние
   │             идентификаторы. Структуру не трогает — только текст.
   ▼
builder.py    — собирает финальный .docx: шапка, метаданные (только
   │             клиентский набор полей), разделы, блок "Требует уточнения"
   │             для отсутствующих обязательных разделов
   ▼
DEV-XXXXX_client.docx
```

**Резервный путь.** Если файл НЕ похож на экспорт Yandex Tracker (нет
`descriptionArea` в разметке — например, выгрузка из другого трекера или
настоящий бинарный `.doc`), агент автоматически переключается на общий
путь через `converter.py` + `analyzer.py`, где структуру ищет и
восстанавливает уже сама модель — это менее точно, но работает с любым
форматом «на коленке».

## Использование

```bash
# базовый вариант: только оформление, без переписывания текста и без API
python agent.py DEV-37598.doc

# переписать текст для заказчика (убрать техжаргон, деловой стиль)
python agent.py DEV-37598.doc --rewrite -o report_for_client.docx

# переписать только конкретные разделы, остальные останутся как в системе
python agent.py DEV-37598.doc --rewrite --rewrite-sections "Потребность клиента"

# разрешить менять названия статусов/полей/объектов (по умолчанию сохраняются дословно)
python agent.py DEV-37598.doc --rewrite --rewrite-terminology

# только проверить полноту задачи, без создания документа (без API)
python agent.py DEV-37598.doc --check-only

# показать в документе ещё и "Техническая реализация" (по умолчанию скрыт)
python agent.py DEV-37598.doc --rewrite --include-technical

# со своим фирменным стилем
python agent.py DEV-37598.doc --rewrite --logo company_logo.png --company "ООО «Ромашка», отдел разработки"

# не показывать блок "Требует уточнения" по отсутствующим разделам
python agent.py DEV-37598.doc --rewrite --hide-gaps

# не показывать скриншоты из задачи вообще
python agent.py DEV-37598.doc --hide-screenshots

# свой список обязательных/исключаемых разделов и полей метаданных
python agent.py DEV-37598.doc --sections-config my_sections.json
```

## Имя итогового файла

По умолчанию (без `-o`): `<ID задачи в системе заказчика>_<Название задачи>.docx`.
Если у задачи нет ID заказчика (поле «Идентификатор задачи клиента» пустое,
либо там ссылка, а не короткий идентификатор — использовать URL как имя
файла бессмысленно) — используется ключ самой задачи в Yandex Tracker,
например `DEV-56712_Клиентская приоритизация заявок на подбор Nestle.docx`.

## Скриншоты из задачи

Реальные скриншоты внутри юзерстори — это ссылки на вложения Трекера вида
`/ajax/v2/attachments/12345?inline=true`, которые требуют авторизованной
сессии Tracker. **Сам пиксель картинки вшить в `.docx` нельзя** — ни у
CLI, ни у HTML-версии нет доступа к вашей сессии. Вместо этого агент
находит домен вашего Трекера прямо в экспортированном файле (по
пермалинку на саму задачу) и вставляет рабочую ссылку «🖼 image.png:
открыть в Tracker» на месте картинки — раньше картинки просто молча
пропадали, теперь видно, что там было вложение, и можно перейти к нему.

По умолчанию скриншоты показываются везде, `--hide-screenshots` выключает
полностью (глобальный переключатель, без разбивки по разделам). Скриншоты,
найденные внутри ячеек таблиц (например, прямо в строке сценария Given/
When/Then), тоже подхватываются — раньше терялись молча, теперь выводятся
после таблицы с указанием, из какой строки они взяты. В HTML-версии такие
скриншоты тоже можно загрузить руками (интерактивный список «Скриншоты» —
агент сам находит место, вам остаётся прикрепить файл).

Пример `my_sections.json` — см. `sections_example.json` в этой папке.
Ключи: `required_sections` (что обязательно должно быть в задаче),
`exclude_from_client` (какие найденные разделы не попадают в клиентский
документ, например «Техническая реализация»), `metadata_fields` (какие
поля из шапки Трекера показывать заказчику — **по умолчанию пусто**:
статус, даты создания/обновления, дедлайн и подобные рабочие поля
заказчику не показываются вообще. Если что-то из этого нужно —
перечислите явно, например `["Проект", "Дедлайн"]`), `client_task_id_field`
(точное название кастомного поля с ID задачи в системе заказчика — по
умолчанию агент сам находит поле по словам "идентификатор"+"клиент" в
названии, но если в вашей очереди оно называется иначе — укажите точно).

## Раздел «Бизнес-кейс»

Агент проверяет, есть ли в задаче раздел «Бизнес-кейс» — двумя способами:
как обычный заголовок (h1-h4, ищется по подстроке «Бизнес-кейс»/«бизнес
кейс», регистронезависимо), и как сворачиваемый блок YFM
(`<details><summary>Бизнес-кейс ...</summary>`) — в Tracker бизнес-кейс
нередко оформляют именно спойлером, а не заголовком. Во втором случае
агент выносит его в отдельный раздел документа на то же место, где он
встретился в исходной задаче — дальше он ничем не отличается от обычного
раздела с таким заголовком.

Если найден (любым из двух способов) — оформляется отдельным визуальным
блоком в документе (мягкая фиолетовая заливка + акцентная полоса), чтобы
заказчик сразу видел самое важное — «зачем это нужно». Скриншоты внутри
раздела (плейсхолдер-плашка или реально загруженная картинка через
HTML-версию) получают ту же рамку — не выпадают из общего блока белым
пятном. Если не найден — печатается рекомендация в консоли
(`❗ Рекомендация: ...`) и добавляется такая же плашка в конец самого
`.docx`; в HTML-версии то же самое видно на шаге «Проверка задачи»
ещё до сборки документа.

Скрыть раздел «Бизнес-кейс» из клиентского документа можно как любой
другой раздел — через `exclude_from_client` в конфиге (CLI) или через
чипы «Разделы, скрываемые из клиентского документа целиком» (HTML).

При `--rewrite`, если раздела нет, Claude сам составит короткий
бизнес-кейс (2–4 предложения) **на основе уже сказанного** в остальных
разделах задачи — ничего не выдумывая сверх того, что там есть — и
вставит его сразу после «Потребность клиента», с пометкой «✍️ Черновик —
проверьте перед отправкой заказчику». Отключается флагом
`--skip-business-case-draft` (CLI) или чекбоксом «Дописать «Бизнес-кейс»,
если отсутствует» (HTML, включён по умолчанию).

## Вопросы на грумминг

Ищутся оба написания — «грумминг» и «груминг» (с одной/двумя «м»), в любом
падеже («для груминга», «на грумминге»). Раньше вопрос на грумминг
детектировался, только если стоял отдельной строкой; на практике его часто
пишут посреди обычного текста в «Детали реализации» — агент теперь режет
такой абзац/пункт списка на предложения, вычленяет груминг-предложения в
отдельную цветную выноску «Требуется грумминг», а остальной текст остаётся
на месте, очищенным.

Упоминания внутри **ячеек таблиц** (например, в структурированной таблице
сценариев, а не в Given/When/Then) из ячейки никуда не выносятся — вырезать
середину ячейки означало бы оставить дыру в табличных данных. Вместо этого
нужный фрагмент подсвечивается точечно прямо на месте (жирным + тем же
светло-синим фоном, что и у выноски в тексте), а остальной текст ячейки
остаётся как есть. Если вопрос в скобках растянут на несколько предложений
и слово «грумминг» встречается только в первом — подсвечивается весь вопрос
целиком (учитывается баланс скобок), а не только первая часть.

Индикатор «есть упоминания груминга» видит оба случая — и в тексте, и в
таблицах. Переключатель показа/скрытия относится только к выноскам в
обычном тексте: подсветку внутри ячеек таблиц он не убирает (см. причину
выше — это уже часть структуры таблицы, а не отдельный блок).

Показывается по умолчанию — печатается предупреждение в консоли CLI
(`❗ В задаче есть упоминания груминга...`) и то же самое видно на шаге
«Проверка задачи» в HTML-версии ещё до сборки документа. Скрыть выноски
в тексте (не в таблицах) можно флагом `--hide-grooming` (CLI) или чекбоксом
«Показывать заметки про грумминг» (HTML).

## Оформление документа

- Плашка заголовка со светлым фоном: тип задачи + ключ (например
  «ЗАДАЧА DEV-56712») и крупный заголовок. Если в задаче заполнено поле
  «Идентификатор задачи клиента» (кастомное поле Трекера, есть не у всех
  задач) — сразу под ключом выводится и оно, например
  «Задача в системе заказчика: NES-75». Если значение похоже на ссылку —
  оно становится кликабельной гиперссылкой.
- Заголовки разделов — с акцентной цветной полосой слева (навигация по
  документу на глаз, без "простыни" одинакового текста).
- Настоящие таблицы Word (не текст через "|"): тёмная шапка, светлая
  чередующаяся заливка строк, тонкие светло-серые границы.
- Абзацы вида «Важно: …» автоматически превращаются в выделенный блок
  тёплого цвета с акцентной полосой — такие предупреждения из задачи не
  теряются в общем тексте.
- Блок «Требует уточнения» (если не хватает обязательных разделов) —
  такой же выделенный блок, но в предупреждающих красных тонах.
- Колонтитул: ключ задачи + номер страницы ("DEV-56712 · 2 / 5").
- Заголовки — Georgia, текст — Calibri (классическая деловая пара
  "заголовочный шрифт + текстовый").

## Таблицы и списки в документе

Таблицы («Критерии приёмки» в формате Given/When/Then и любые другие
таблицы, встреченные в тексте задачи) рендерятся как настоящие таблицы
Word — с шапкой и чередующейся заливкой строк, а не одним сплошным
абзацем через "|". Списки (в т.ч. вложенные) — как настоящие
маркированные/нумерованные списки Word. Это работает и без `--rewrite`.

Форматирование внутри ячеек сохраняется как в исходной задаче:
**жирный/курсив** (например, если в описании сценария выделено название
поля или объекта) и переносы строк, если в одной ячейке несколько
абзацев — раньше всё это стиралось при разборе и склеивалось в одну
строку сплошным текстом. Вопрос на грумминг внутри ячейки по-прежнему
подсвечивается точечно (см. выше) — если строка одновременно содержит
и исходное форматирование, и вопрос на грумминг, приоритет отдаётся
видимости грумминга (редкий случай пересечения двух типов выделения).

## Что переписывает Claude, а что нет

`--rewrite` работает по умолчанию **консервативно**:

- **Таблицы не трогает вообще** — Given/When/Then из «Критерии приёмки» и
  любые другие таблицы в Claude не отправляются и остаются настоящей
  таблицей Word как есть.
- **Названия статусов, полей форм и объектов системы сохраняются дословно**
  — по умолчанию Claude может переписать только связность и стиль текста,
  убрать программный мусор (имена классов/триггеров/джобов в коде, пути к
  полям БД), но не может переименовать то, что называется в самой системе
  (например статус «Подбор кандидатов» или поле «Дата собеседования»).
  Если всё же нужно упростить и такие названия — добавьте
  `--rewrite-terminology`.
- **Переписывает все разделы**, если не указано иное — сузить до конкретных
  можно через `--rewrite-sections "Раздел 1" "Раздел 2"`; остальные разделы
  тогда вообще не уйдут в API и останутся как в системе.

## Переименование заголовков в документе

«Потребность клиента» в исходной задаче показывается в итоговом `.docx`
как «Потребность заказчика» — это только отображение в финальном
документе, вся внутренняя логика (проверка обязательных разделов,
`--rewrite-sections` и т.п.) продолжает ссылаться на исходное название
из системы. Список переименований — `HEADING_DISPLAY_OVERRIDES` в
`builder.py`, если нужно что-то ещё переименовать для заказчика.

## Что выводит проверка полноты

При каждом запуске (кроме `--check-only`, где это единственный вывод)
в консоль печатается отчёт вида:

```
=== Проверка полноты задачи ===
  ✅ Проблематика
  ✅ Описание задачи
  ❌ Бизнес-кейс
  ✅ Критерии приёмки
  ❌ Ожидаемый результат
  ❌ Сроки / оценка

⚠ Отсутствуют разделы (3): Бизнес-кейс, Ожидаемый результат, Сроки / оценка
  Рекомендуется уточнить у автора задачи перед отправкой заказчику.
```

По умолчанию отсутствующие разделы всё равно попадают в итоговый .docx
с пометкой курсивом красного цвета «Не указано в исходной задаче» —
чтобы менеджер видел пробелы прямо в документе перед отправкой. Флаг
`--hide-gaps` убирает такие разделы из документа полностью.

## Пакетная обработка (несколько задач подряд)

```bash
for f in tasks/*.doc; do
  python agent.py "$f" --rewrite -o "clients/$(basename "${f%.doc}")_client.docx"
done
```
- **Более умный разбор нестандартных таблиц** в «Критерии приёмки» —
  сейчас размечены только Given/When/Then; остальное см. раздел
  "Известное ограничение" выше.
